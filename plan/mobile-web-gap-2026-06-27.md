# Mobile ↔ Web Feature-Gap Plan (audit 2026-06-27)

> Generated by adversarial 11-domain audit (map → skeptic-verify → synthesize). Scope: the two personas the mobile app serves — **Customer** and **Employee**. Manager/Admin desktop tooling intentionally excluded.

## Executive summary

The mobile app already ships the customer happy paths (browse/filter, vehicle detail pricing, create-booking + PhonePe payment, trips list, QR pass, profile/edit) and the employee basics (dashboard stats, scan-to-pickup/return, cash shift open/close, KYC verify). But several CORE flows are broken or dead-ended, and one whole flow is missing. Customer side: KYC upload is hard-broken (POST omits the mandatory FRONT/BACK `side` so every upload 400s), which blocks any KYC-required booking end-to-end; and the otherwise-working checkout is missing coupon, advance-vs-full plan, a T&C gate, and a real confirmation screen. Employee side carries most of the weight: pickup AND return screens hard-disable the confirm button whenever an advance booking has a remaining balance with no way to collect it (a literal dead-end), the return flow cannot compute km/fuel/damage charges or settle/refund the deposit, and the entire walk-in booking creation flow (customer create -> vehicle pick -> KYC -> summary/hold/pay) does not exist on mobile at all. The gap is large but concentrated: ~9 P0 items unblock or build core flows. Highest leverage, in order: (1) fix customer KYC upload, (2) add remaining-balance collection so employee pickup/return can complete, (3) make the return flow compute charges + settle, (4) build the walk-in booking flow, then (5) finish customer checkout (coupon/advance/terms/confirmation) and (6) add date+time so duration-aware pricing is reachable. A handful of items need backend work first and are flagged (customer remaining-balance fields on the bookings list, OTP cookie->body patch, Google token-exchange, HOLD payment re-initiate).
